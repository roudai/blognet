# Feature Specification: サイト基盤

**Feature Branch**: `001-site-foundation`

**Created**: 2026-11-22

**Status**: Draft

**Input**: User description: "blog.roudai.net(ブログ版ろーだいねっと)を Nuxt 2 から最新の安定版 Nuxt + TypeScript(静的生成のみ)へ再構築する、その最初の機能として「サイト基盤」を作る。対象は共通レイアウト、ヘッダー、フッター、トップページの骨組み、GitHub Pages へのデプロイ基盤、CI 品質ゲートである。記事ページ本体とトップページの記事一覧は別の Spec で扱う。方針は roudai.net の再構築と同じにする。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 全ページ共通のヘッダーとフッターを表示する (Priority: P1)

訪問者は、サイトのどのページを開いても、同じヘッダー(サイト名リンク「ブログ版ろーだいねっと アーカイブ」、GitHub リンク)と同じフッターを見ることができる。本文は、現行サイトと同じく、画面の中央の半分の幅に表示される。

**Why this priority**: 基盤の中心となる機能であり、後続の Spec(記事ページの移植)がすべてこの共通レイアウトの上に載る。これだけでも、サイトの骨格として動作を確認できる。

**Independent Test**: トップページを開き、ヘッダーとフッターが現行サイトと同じ内容と見た目で表示されること、本文の幅と位置が現行サイトと同じであることを確認する。

**Acceptance Scenarios**:

1. **Given** 訪問者がデスクトップ幅でトップページを開いている、**When** ヘッダーを見る、**Then** 濃い色の帯に、サイト名リンクと GitHub アイコンのリンクが、現行サイトと同じ並びで表示される。
2. **Given** 訪問者がヘッダーのサイト名を選ぶ、**When** リンクを開く、**Then** トップページ(`/`)へ移動する。
3. **Given** 訪問者が GitHub アイコンを選ぶ、**When** リンクを開く、**Then** 現行サイトと同じ外部の URL へ移動する。
4. **Given** 訪問者が任意のページを開いている、**When** ページ下部までスクロールする、**Then** 現行サイトと同じ内容のフッター(© 2012-{年} roudai.net と GitHub アイコン)が表示される。

---

### User Story 2 - 運営者が安全に変更を統合し、公開できる (Priority: P2)

運営者は、機能ごとの作業ブランチを統合ブランチ(`nuxt4-rebuild`)へ PR でマージして、移植を進められる。PR では Lint、型チェック、静的生成のビルド確認が自動で実行され、結果が分かる。これらに失敗した変更はマージできない。本番への公開は `main` へのマージ時だけ自動で行われ、PR やブランチへの push では公開されない。

**Why this priority**: 以降の移植の Spec が、この品質ゲートの上で進む。また、公開の経路をここで決めておかないと、移行途中の状態を誤って本番へ出すおそれがある。

**Independent Test**: 統合ブランチ宛ての PR を作り、Lint、型チェック、ビルド確認が自動で実行されること、公開が行われないことを確認する。

**Acceptance Scenarios**:

1. **Given** `main` または `nuxt4-rebuild` 宛ての PR が作られた、**When** PR の確認が実行される、**Then** Lint、型チェック、静的生成のビルドが実行され、その結果が PR 上で確認できる。
2. **Given** Lint または型チェックが失敗する変更がある、**When** PR をマージしようとする、**Then** マージできない。
3. **Given** PR またはブランチへの push が行われた、**When** 確認が完了する、**Then** 本番サイトは更新されない。
4. **Given** 変更が `main` へマージされた、**When** 公開の処理が実行される、**Then** 生成されたサイトが `https://blog.roudai.net` へ公開される。
5. **Given** 全移植と切り替えチェックリストが完了していない、**When** 運営者が公開の可否を判断する、**Then** `main` へのマージは行わない運用であることが、リポジトリの文書から分かる。

---

### User Story 3 - 公開物に必要なファイルが含まれ、広告が含まれない (Priority: P3)

運営者が公開したサイトでは、独自ドメインを維持するためのファイル(`CNAME`)が、サイトのルートに存在する。一方、Web サイトには Google 広告の表示や、そのためのファイル(`ads.txt`)が含まれない。

**Why this priority**: 公開時に必須の条件だが、レイアウトや CI が先に整ってから確認できる。切り替え時のチェックリスト項目でもある。

**Independent Test**: 静的生成の出力を調べ、`CNAME` が存在すること、`ads.txt` と広告関連のスクリプトや要素が存在しないことを確認する。

**Acceptance Scenarios**:

1. **Given** サイトを静的生成した、**When** 出力のルートを確認する、**Then** `CNAME`(内容は `blog.roudai.net`)が存在する。
2. **Given** 生成したサイト、**When** `/ads.txt` を要求する、**Then** 存在しない(404)。
3. **Given** 生成したサイトの任意のページ、**When** ページの内容を確認する、**Then** Google 広告のスクリプト、広告枠、広告用の meta タグが含まれない。

---

### User Story 4 - トップページの骨組みを確認できる (Priority: P3)

訪問者がトップページ(`/`)を開くと、共通のヘッダーとフッターに挟まれた、トップページの骨組みが表示される。トップページの中身(記事一覧の移植)は、後続の Spec で行う。

**Why this priority**: 共通レイアウトの動作確認と、デプロイ経路の確認に使う最小のページである。内容の移植は範囲外のため、優先度は低い。

**Independent Test**: `/` を開き、エラーなく表示され、ヘッダーとフッターが含まれることを確認する。

**Acceptance Scenarios**:

1. **Given** 訪問者が `/` を開く、**When** ページが表示される、**Then** エラーなく表示され、共通のヘッダーとフッターが含まれる。

---

### Edge Cases

- 狭い画面(1024px 未満)で閲覧した場合: 現行サイトは、ヘッダーにバーガーボタンがなく、GitHub アイコンのリンクが表示されない(Bulma の `navbar-menu` が隠れる)。パリティ(原則 IV)のため、新サイトも同じ挙動にする。メニューの開閉の追加は機能追加にあたるため、この Spec では行わない。
- 本文の幅: 現行は 769px 以上で画面の半分の幅、768px 以下で全幅になる。新サイトも同じ切り替えにする。
- PR の確認が失敗した場合: どの工程(Lint、型チェック、ビルド)が失敗したかを、PR 上で判別できる。
- 公開の処理が失敗した場合: 直前に公開されていたサイトがそのまま残り、壊れた状態のサイトは公開されない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: サイトは、すべてのページで共通のヘッダーとフッターを表示しなければならない(MUST)。
- **FR-002**: ヘッダーは、サイト名リンク(`/` へのリンク、表示名は現行と同じ)と GitHub アイコンのリンクを、現行サイト(`legacy/components/NavBar.vue`)と同じ並びとリンク先で含まなければならない(MUST)。
- **FR-003**: フッターは、「© 2012-{年} roudai.net」と GitHub アイコンのリンクを、現行サイト(`legacy/components/FooterBar.vue`)と同じ内容とリンク先で含まなければならない(MUST)。
- **FR-004**: ヘッダー、フッター、本文の幅と余白の見た目は、狭い画面と広い画面の両方で現行サイトと同等でなければならない(MUST)。デザインの刷新や、メニューの開閉などの機能の追加を行ってはならない(MUST NOT)。
- **FR-005**: トップページ(`/`)は、共通レイアウトを含む骨組みとして表示されなければならない(MUST)。記事一覧の移植は、この Spec の対象外とする。
- **FR-006**: 記事ページ(`/post-37`、`/post-386`、`/post-388`、`/post-535`、`/post-700`)の移植は、この Spec の対象外とする。
- **FR-007**: サイトは、最新の安定版の Nuxt と TypeScript で構築し、静的生成のみで出力しなければならない(MUST)。サーバーの実行環境を必要としてはならない(MUST NOT)。
- **FR-008**: `main` または `nuxt4-rebuild` 宛ての PR では、Lint、型チェック、静的生成のビルド確認が自動で実行されなければならない(MUST)。この確認は、本番へ公開してはならない(MUST NOT)。
- **FR-009**: Lint または型チェックに失敗した変更は、マージできてはならない(MUST NOT)。マージを止める手段は、リポジトリの設定で運営者が構成する。
- **FR-010**: 本番への公開は、`main` へのマージ時にだけ自動で実行されなければならない(MUST)。公開先は `https://blog.roudai.net` とする。
- **FR-011**: 全移植と切り替えチェックリストが完了するまで `main` へマージしない運用と、`nuxt4-rebuild` を統合ブランチとして使う運用を、リポジトリの文書に記載しなければならない(MUST)。
- **FR-012**: 生成したサイトのルートには、`CNAME`(内容は `blog.roudai.net`)が含まれなければならない(MUST)。
- **FR-013**: 生成したサイトには、`ads.txt`、Google AdSense のスクリプトや広告枠、広告用の meta タグ、広告表示を前提にしたレイアウトの余白を含めてはならない(MUST NOT)。
- **FR-014**: パッケージマネージャーとロックファイルは、それぞれ1つに統一しなければならない(MUST)。`yarn.lock` を引き継いではならない(MUST NOT)。
- **FR-015**: `legacy/` 配下のファイルを変更してはならない(MUST NOT)。参照用にのみ使う。

### Key Entities *(include if feature involves data)*

- **公開物のルートファイル**: 生成したサイトのルートに置く `CNAME` と `favicon.ico`。独自ドメインの維持とタブのアイコンに使う。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ヘッダーとフッターのリンク(表示名とリンク先)が、現行サイトと同じで、不足や相違が0件である。
- **SC-002**: 狭い画面と広い画面の両方で、ヘッダー、フッター、本文の幅を現行サイトと並べて比較したとき、色、余白、幅に、運営者が気づく相違がない。
- **SC-003**: `main` または `nuxt4-rebuild` 宛ての PR を作ってから、Lint、型チェック、ビルド確認の結果が出るまでの時間が、15分以内である。
- **SC-004**: PR やブランチへの push では、本番サイトの更新が0回である。
- **SC-005**: 静的生成の出力で、`CNAME` が存在し、`ads.txt` と広告関連の要素が0件である。
- **SC-006**: Lint、型チェック、静的生成が、クリーンな環境から手順書どおりに実行して、すべて成功する。

## Assumptions

- 訪問者は、モバイルとデスクトップの一般的な最新ブラウザーで閲覧する。
- 現行のヘッダーとフッターの内容(項目、リンク先、見た目)は、`legacy/` にあるソースと、公開中の `https://blog.roudai.net` を正とする。
- 技術選定(CSS の手段、Buefy の代替、デプロイの方式など)は、この Spec には含めず、Plan で決める。同じ運営者の roudai.net の再構築で採用した構成を優先して使う。原則 VIII のとおり、採用前に spike で検証する。
- CI で必要なマージの制限(ブランチ保護)と、GitHub Pages の公開方式の設定は、リポジトリの設定で運営者が行う。設定そのものはリポジトリの外にある。
- AdSense の管理画面など、リポジトリの外にある広告関連の設定は、この Spec の対象外とする。
- テストコードは、この Spec では必須としない。ただし、Lint と型チェックは必須である(原則 V)。
